# SECURITY & RESPONSIBLE DISCLOSURE

## Что делать, если вы нашли уязвимость

### В самом проекте hackbook

Если вы нашли проблему в **инструментах, сайте или лабораториях** проекта
(например, лаборатория доступна не только с `127.0.0.1`, скрипт выполняет
произвольный код при разборе чужого Markdown, в CI утекают секреты):

1. **Не создавайте публичное issue** с деталями.
2. Напишите мейнтейнерам приватно:
   * GitHub → вкладка **Security → Report a vulnerability** (private vulnerability reporting);
   * либо e-mail из раздела «Контакты» профиля репозитория.
3. Укажите: компонент, версию/коммит, шаги воспроизведения, влияние,
   возможное исправление.
4. Мы отвечаем в течение **5 рабочих дней**, статус обновления — не реже
   раза в неделю. Целевой срок исправления критичных проблем — **14 дней**.
5. Если вы хотите опубликовать разбор — согласуйте дату; мы дадим атрибуцию
   в разделе благодарностей и (при желании) в security-адвайзори.

### В стороннем продукте, описанном в карточке

Карточки описывают **классы** уязвимостей, а не конкретные продукты.
Если в процессе работы вы нашли уязвимость в реальном вендорском ПО:

1. Не публикуйте детали и не добавляйте их в этот репозиторий.
2. Сообщите вендору напрямую (bug bounty / security-контакт / координация
   через CERT).
3. В репозиторий можно добавить **обезличенную** карточку техники: без названий
   продуктов, без рабочего эксплойта против живой цели, с секциями
   `Detection` и `Remediation`.

## Границы допустимого контента

Принимаем:

* описания классов уязвимостей и техник с оборонительной перспективой;
* payload'ы для диагностики, воспроизводимые в лабораториях проекта;
* правила детектирования, чек-листы hardening, разборы инцидентов
  (без идентифицирующих данных);
* словари из открытых источников с указанием источника и лицензии.

**Не принимаем:**

* готовое вредоносное ПО (шифровальщики, стиллеры, руткиты, дропперы, C2),
  а также инструкции по их сборке и доставке;
* обфускацию и техники обхода защитных решений, представленные как
  «инструкция по обходу», а не как материал для детектирования;
* payload'ы, нацеленные на отказ чужой инфраструктуры (DDoS-усиление
  против конкретных целей, массовые рассылки);
* реальные учётные данные, ключи, токены, персональные данные, дампы утечек;
* инструкции по атаке на конкретные живые сервисы, организации и людей;
* материалы, нарушающие экспортные ограничения или санкции.

Модерация: любой PR с спорным содержанием выносится на обсуждение
мейнтейнеров; решение фиксируется в комментарии к PR с обоснованием.

## Безопасность лабораторий

Лаборатории намеренно уязвимы. Требования, которые мы соблюдаем и просим
соблюдать контрибьюторов:

* порты публикуются только на `127.0.0.1`;
* контейнеры: non-root, `cap_drop: [ALL]`, `read_only: true`,
  `no-new-privileges`, `healthcheck`;
* сеть лабораторий изолирована; для полного запрета egress используйте
  `internal: true` в `labs/setup/docker-compose.yml`;
* в образах нет реальных секретов, ключей и персональных данных;
* `tools/payload-tester.sh` отказывается отправлять запросы на цели
  вне `localhost`/`*.local` без явного `HACKBOOK_ALLOWED_TARGETS`;
* README каждой лабы содержит предупреждение об ответственном использовании.

Если вы обнаружили, что какое-то из этих требований нарушено — это
**критичная** проблема проекта, сообщайте по каналу выше.

## Поддерживаемые версии

Проект до 1.0 не имеет LTS-веток: поддерживается только `main`.
Релизы помечаются тегами `v0.x.y`; PDF/EPUB соответствующей версии
прикрепляются к релизу на GitHub.

## Правовая оговорка

Материалы предоставляются «как есть», без гарантий. Авторы не несут
ответственности за применение знаний. Использование техник против систем
без письменного разрешения владельца нарушает законодательство большинства
стран (в РФ — ст. 272–274 УК; в США — CFAA; в ЕС — директива 2013/40/EU
и национальные аналоги). Работая с проектом, вы подтверждаете, что используете
его в учебных целях, в своих лабораториях или в рамках авторизованных
тестирований на проникновение.
