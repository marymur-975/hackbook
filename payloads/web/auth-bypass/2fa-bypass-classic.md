# Обход 2FA: прямая навигация и повтор использования токена

!!! warning "Этика"
    Только лаборатории `hackbook` или системы с письменным разрешением на тестирование.

## Payload
```
POST /account/verify  ->  GET /account/settings (минуя шаг 2FA)
```

## Explanation

Типовые ошибки реализации второго фактора:

1. Состояние «2FA пройдена» хранится в клиентском cookie/параметре
   (`2fa_passed=1`) — подделывается.
2. Защищённые страницы проверяют только наличие сессии, а не факт прохождения 2FA.
3. Одноразовый код не инвалидируется после использования (replay).
4. Отсутствие лимита попыток — перебор 4–6 значного кода реалистичен
   (10^6 вариантов при отсутствии блокировки).
5. Код возвращается в ответе/письме до проверки (утечка в теле ответа).
6. Сброс пароля обходит 2FA: flow «забыл пароль» даёт новую сессию без второго фактора.

## Detection

1. Пройдите аутентификацию до шага 2FA и попробуйте напрямую открыть защищённый URL.
2. Изучите cookie/параметры на шаге 2FA — есть ли клиентские флаги.
3. Повторите запрос с уже использованным кодом (replay).
4. Проверьте лимит попыток и время жизни кода.
5. Пройдите flow сброса пароля — требуется ли 2FA.

## Remediation

- Состояние 2FA — только серверное, привязанное к сессии, с флагом «полностью аутентифицирован».
- Проверка этого флага в middleware для всех защищённых маршрутов.
- Одноразовые коды: инвалидация после первой проверки, TTL 30–60 с, лимит попыток (3–5).
- Rate limiting по учётке и IP, экспоненциальная задержка.
- 2FA обязательна для сброса пароля и смены e-mail.
- Предпочтение TOTP/WebAuthn вместо SMS; резервные коды — одноразовые.
