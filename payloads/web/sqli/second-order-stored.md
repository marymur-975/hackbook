# SQLi второго порядка: сохранённое значение исполняется позже

!!! warning "Этика"
    Только лаборатории `hackbook` или системы с письменным разрешением на тестирование.

## Payload
```
# Сценарий 1: сохранение в профиле, использование в отчёте
#  шаг 1 — сохраняем полезную нагрузку через параметризованный запрос
#          (она БЕЗОПАСНО записывается в БД как строка)
#  шаг 2 — позже другой код читает её и подставляет в динамический SQL
#
# значение для сохранения (поле «имя организации»):
ACME' UNION SELECT password_hash, api_key FROM users--
#
# уязвимый код второго порядка (отчёт/выгрузка):
#   name = db.query("SELECT org_name FROM profile WHERE id=?", [id])
#   db.query("SELECT * FROM sales WHERE org='" + name + "'")   # <- инъекция

# Сценарий 2: имя пользователя -> логирование -> аналитический запрос
# значение при регистрации:
user' OR '1'='1

# Сценарий 3: данные из внешнего источника (API партнёра, CSV-импорт)
# содержимое ячейки CSV:
1; DROP TABLE sessions--
# импорт: INSERT INTO t VALUES ('" + cell + "')

# Сценарий 4: имя поля из конфигурации -> ORDER BY в запросе списка
# сохранённая настройка сортировки:
name; SELECT SLEEP(5)--

# Сценарий 5: JSON-атрибут -> динамический запрос в аналитике
# {"filter": "status='active' UNION SELECT ..."}

# Как искать в своём коде (ревью):
#   grep -rn "SELECT .*\" *+" --include=*.java --include=*.cs .
#   grep -rnE "(query|execute|raw)\(.*%s|\+ *[a-z_]+" --include=*.py .
#   grep -rn "\${.*}" --include=*.js src/ | grep -i query
```

## Explanation

**Инъекция второго порядка** (second-order / stored SQLi) возникает,
когда значение сохраняется безопасно (через параметризованный запрос),
а затем **другой код** читает его и подставляет в динамический SQL
без параметризации.

Почему это опасно и трудно обнаруживается:

* точка входа защищена: на входе всё параметризовано, и сканеры/
  пентестеры видят «безопасный» код;
* срабатывает в другом месте и в другое время: отчёты, batch-задачи,
  cron, админ-панели, миграции, аналитика;
* выполняется часто от более привилегированной учётки (сервис отчётов,
  ETL, админ-панель), что расширяет последствия;
* источник данных может быть «доверенным»: данные партнёра, импорт CSV,
  внутренняя конфигурация, значение из другой БД.

Типовые места исполнения:

1. Формирование `WHERE`/`ORDER BY` из сохранённых настроек пользователя.
2. Генерация отчётов и выгрузок (динамические фильтры).
3. ETL/миграции, читающие «сырые» данные из staging-таблиц.
4. Админ-интерфейсы с поиском по полям, заполненным пользователями.
5. Шаблоны уведомлений/писем, где значение подставляется в SQL-запрос
   (например, «показать последние заказы клиента»).
6. Плагины и кастомные поля (метаданные), используемые в запросах.

Правило: **доверие не наследуется**. Значение, пришедшее от пользователя,
остаётся недоверенным всю жизнь — в любом месте, где оно используется.
Параметризация нужна не на входе, а в каждом запросе.

## Detection

* SAST: поиск динамической склейки SQL во всех слоях, включая модули
  отчётов, ETL и админ-панели (не только «входные» контроллеры).
* Логирование SQL с указанием источника значений: запросы, построенные
  из сохранённых строк, помечаются (например, по стектрейсу модуля
  отчётов).
* Алерты на синтаксические ошибки СУБД в batch-задачах и отчётах —
  классический признак second-order инъекции.
* Поиск в БД: значения в пользовательских полях, содержащие
  `'`, `--`, `UNION`, `SELECT`, `;` (см. ниже SQL-запрос).
* Аудит-лог изменений данных: кто и когда записал подозрительное
  значение (важно для расследования: эксплуатация может произойти
  через недели).
* WAF здесь почти бесполезен: полезная нагрузка приходит через
  легитимный параметризованный запрос.

## Remediation

- Параметризация **в каждом** запросе, независимо от происхождения
  данных; запрет конкатенации в отчётах, ETL и админ-модулях.
- `ORDER BY`/имена полей — только whitelist, даже если значение
  сохранено в настройках пользователя.
- Валидация на входе по структуре (charset, длина, формат) — снижает
  шанс сохранить полезную нагрузку, но не заменяет параметризацию.
- Минимальные права для сервисов отчётов и ETL (read-only, отдельные
  учётки, только нужные таблицы).
- Регулярный скан БД на «SQL-подобные» значения в текстовых полях:

```sql
SELECT id, org_name FROM profile
 WHERE org_name LIKE '%--%' OR org_name LIKE '%UNION SELECT%'
    OR org_name LIKE '%; DROP%' OR org_name LIKE '%SLEEP(%';
```

- Разделение слоёв: данные пользователей не должны попадать в код
  построения запросов; если нужен «динамический фильтр» —
  используйте структуру (DSL/JSON-схему), а не SQL-строку.
- Тесты: в интеграционных тестах сохранять инъекционные строки, а затем
  прогонять отчёты/выгрузки и проверять отсутствие синтаксических ошибок.

## Detection rules

```yaml
title: First-order маркеры — SQL-синтаксис сохраняется в пользовательских данных
id: e5f6a7b8-0040-4e5f-9a7b-000000000040
status: experimental
description: >-
  Пользователь сохраняет в профиле/комментарии/тикета значение с SQL-маркерами
  (UNION SELECT, тавтология, комментарий-терминатор). Само по себе сохранение
  безопасно, но эти строки — закладки second-order инъекции: детектируйте их
  на входе и ищите в ошибках БД позже.
references:
  - https://attack.mitre.org/techniques/T1190/
logsource:
  category: application
  definition: 'логи приложения: действия записи пользовательских данных с телом запроса'
detection:
  stored_action:
    event_action:
      - profile_update
      - comment_create
      - registration
      - support_ticket
  sql_marker:
    request_body|contains:
      - "' UNION SELECT"
      - "' OR '1'='1"
      - "'-- -"
      - "' -- -"
      - "' AND 1=1"
  condition: stored_action and sql_marker
fields:
  - source_ip
  - request_path
  - event_action
  - request_body
falsepositives:
  - пользователи-разработчики, обсуждающие SQL в комментариях (редко в полях профиля)
level: high
tags:
  - attack.initial_access
  - attack.t1190
  - cwe.89
```
