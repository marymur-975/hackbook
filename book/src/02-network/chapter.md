# Сетевая безопасность: разведка, сервисы, сегментация

Веб-уязвимость даёт доступ к одному приложению. Сетевая — к сегменту, а часто и
ко всей внутренней инфраструктуре. Причина почти всегда одна: сервисы, рассчитанные
на доверенную сеть, оказываются доступны всем.

## Карта типовых портов

| Порт | Сервис | Что даёт атакующему | Чем лечится |
|------|--------|---------------------|-------------|
| 21 | FTP | Анонимный доступ, запись в веб-корень, открытый текст | SFTP/FTPS, отключение anonymous |
| 22 | SSH | Перебор, слабые ключи, старые версии | Ключи + 2FA, `PasswordAuthentication no` |
| 23 | Telnet | Пароли в открытом виде | Только SSH/консольный сервер |
| 25/587 | SMTP | Open relay, фишинг с «своего» домена | Требуется AUTH, SPF/DKIM/DMARC |
| 53 | DNS | AXFR, усиление, отравление кеша | ACL на transfer, DNSSEC |
| 88/464 | Kerberos | AS-REP roasting, golden ticket | см. главу про AD |
| 135/139/445 | SMB/RPC | Null session, relay, shares, MS17-010-класс | Подпись SMB, сегментация, патчи |
| 161 | SNMP | Конфигурации, ARP, процессы | SNMPv3 authPriv |
| 389/636/3268 | LDAP(S)/GC | Перечисление домена, учётки | Требовать bind, LDAPS |
| 1433 | MSSQL | `xp_cmdshell`, данные | Не наружу, не `sa` |
| 3306/5432 | MySQL/PostgreSQL | Дамп БД | Только из app-сегмента |
| 3389 | RDP | Перебор, BlueKeep-класс | NLA, VPN/RDG, MFA |
| 5985/5986 | WinRM | Удалённое выполнение | Только управляющий сегмент |
| 6379/11211/27017 | Redis/Memcached/Mongo | Данные без аутентификации, RCE | `requirepass`, `bind 127.0.0.1` |
| 9200 | Elasticsearch | Индексы без пароля | X-Pack security, TLS |
| 2375/2376 | Docker API | Root на хосте | Только TLS+сертификаты, не наружу |
| 6443/10250/2379 | Kubernetes | API, kubelet exec, etcd-секреты | RBAC, webhook-авторизация kubelet |

## Разведка: порядок действий

Разведка в учебном стенде — это не «запустить все сканеры», а последовательная
проверка гипотез. Порядок, который экономит время:

```bash
# 1. живые хосты и топология
nmap -sn 10.10.10.0/24

# 2. быстрые TCP-порты (top-1000) + определение сервисов
nmap -sS -sV --top-ports 1000 -oA scan/fast 10.10.10.0/24

# 3. UDP — то, что все забывают: DNS, SNMP, NetBIOS, TFTP, IPMI
nmap -sU --top-ports 50 -oA scan/udp 10.10.10.0/24

# 4. все порты на интересных хостах (медленно, но обязательно)
nmap -p- -T4 --min-rate 1000 -oA scan/all 10.10.10.5

# 5. скрипты по найденным сервисам
nmap --script "ldap-*,smb-*,snmp-*,dns-*,redis-info,mysql-info" -p 53,161,389,445,3306,6379 10.10.10.5
```

Правило: **каждый открытый порт должен получить объяснение**. Порт 6379 на сервере
приложений — это не «Redis для кеша», это «Redis без пароля, доступный из всей
подсети, с правами записи в файловую систему».

## Сетевые сервисы без аутентификации

Три самых частых сценария в реальных аудиториях:

### Redis/Memcached наружу

```bash
redis-cli -h 10.10.10.5 INFO keyspace        # NOAUTH не получен -> доступа нет вовсе
echo -e 'stats\r\nquit\r' | nc 10.10.10.5 11211
```

Последствия: чтение кеша сессий и токенов, запись в файловую систему
(`CONFIG SET dir` + `SAVE`), загрузка модуля Redis = RCE.
Подробности и защита: `payloads/network/redis-unauthenticated.md`.

### SNMP с community `public`

```bash
onesixtyone -c wordlists/fuzzing/snmp-communities.txt 10.10.10.0/24
snmpwalk -v2c -c public 10.10.10.1 1.3.6.1.2.1.25.4.2   # процессы на устройстве
```

### Анонимный LDAP / null session SMB

```bash
ldapsearch -x -H ldap://10.10.10.5 -s base -b '' '+'      # RootDSE без учётки
rpcclient -U '' -N 10.10.10.5 -c 'enumdomusers'
smbclient -L //10.10.10.5 -N
```

Это входная точка в главу про Active Directory: без учётных данных мы получаем
список пользователей, групп и структуру домена — готовый словарь для атак на пароли.

## Подпись SMB и relay

Отсутствие обязательной SMB-подписи — одна из самых недооценённых находок:
она превращает любой перехват аутентификации (LLMNR/NBNS spoofing, принуждение
через printer bug, вредоносная ссылка на `\\attacker\share`) в доступ к чужой машине.

```bash
# хосты без обязательной подписи
crackmapexec smb 10.10.10.0/24 --gen-relay-list relay.txt
nmap --script smb2-security-mode -p445 10.10.10.0/24
```

Защита — это не «поставить антивирус», а набор политик: SMB-подпись обязательна,
LLMNR/NBT-NS отключены, LDAP-подпись и channel binding на контроллерах,
NTLM ограничен. Разбор: `payloads/network/smb-signing-relay.md`.

## DNS как источник информации

```bash
dig AXFR lab.local @10.10.10.5          # передача всей зоны
dig SRV _ldap._tcp.lab.local @10.10.10.5 # контроллеры домена и их роли
dnsrecon -d lab.local -t std
```

AXFR-запрос с внешнего IP — почти всегда конфигурационная ошибка: передача зоны
предназначена для репликации между NS и должна быть ограничена ACL и TSIG.

## Сегментация: что реально работает

Сегментация — единственная мера, которая ограничивает ущерб независимо от числа
уязвимостей. Минимально рабочая модель:

```
                 ┌─────────────────────────┐
  Internet ───►  │  DMZ: reverse proxy,    │
                 │  WAF, статика           │
                 └───────────┬─────────────┘
                             │ только 443/8080
                 ┌───────────▼─────────────┐
                 │  APP: приложения        │  ──► egress: только нужные API
                 └───────────┬─────────────┘
                             │ только 3306/5432, только с IP app
                 ┌───────────▼─────────────┐
                 │  DATA: СУБД, кеш, брокер│  ──► egress: запрещён полностью
                 └───────────┬─────────────┘
                             │ только 636/88/445 по необходимости
                 ┌───────────▼─────────────┐
                 │  MGMT: AD, мониторинг,  │  доступ только из jump-хоста
                 │  бэкапы, CI/CD          │  + MFA + запись сессий
                 └─────────────────────────┘
```

Практические правила:

1. **Default deny** между сегментами; разрешающие правила — по портам и источникам.
2. **Egress-фильтрация обязательна**: серверы БД и кеша не должны иметь исходящего
   доступа в интернет. Это убивает OOB-эксфильтрацию и reverse-shell.
3. **Jump-хост с записью сессий** для админ-доступа; никаких RDP/SSH «напрямую».
4. **Link-local (169.254.169.254) блокируется** там, где метаданные не нужны —
   иначе любой SSRF становится облачным инцидентом.
5. Правила сегментации **тестируются**: регулярно проверяйте, что из DMZ нельзя
   достучаться до DATA напрямую.

## Практика

```bash
cd labs/network-labs
docker compose up -d            # vulnerable-lab: SNMP, FTP, Redis, LDAP, SMB-имитация
```

Задания:

1. Найдите все сервисы контейнера без аутентификации, зафиксируйте порты и версии.
2. Прочитайте данные Redis и объясните, что из них можно извлечь (сессии, кеш, токены).
3. Получите список пользователей через LDAP anonymous bind.
4. Проверьте, возможен ли AXFR; если да — восстановите карту внутренних имён.
5. Закройте найденное конфигурацией: `requirepass`, `bind 127.0.0.1`, ACL на transfer,
   запрет anonymous bind. Перепроверьте сканером.

### Чек-лист сетевого аудита

- [ ] Инвентаризация всех открытых портов (TCP **и** UDP) по сегментам.
- [ ] Нет сервисов без аутентификации в доступе извне сегмента.
- [ ] Нет учётных данных по умолчанию (`public`/`private`, `admin`/`admin`).
- [ ] Устаревшие протоколы отключены: Telnet, FTP, HTTP, SNMPv1/v2c, SMBv1, TLS < 1.2.
- [ ] Обязательные подписи/шифрование: SMB, LDAP, syslog, SNMPv3.
- [ ] Egress-фильтрация для DATA и MGMT сегментов.
- [ ] DNS: AXFR по ACL, DNSSEC для внешних зон, мониторинг запросов к новым доменам.
- [ ] Админ-доступ только через jump-хост с MFA и записью сессий.
