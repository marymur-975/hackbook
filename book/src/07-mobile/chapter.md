# Mobile & API: OAuth, GraphQL, мобильные хранилища

API — это та же веб-безопасность, но без «браузерного» слоя защиты: здесь нет
CSP, нет same-origin policy в привычном виде, а клиент часто полностью под
контролем пользователя (мобильное приложение распаковывается и патчится за
минуты). Главное отличие от классического веба: **сервер обязан считать клиента
недоверенным целиком**, включая официальное приложение.

## Модель угроз API

```
┌───────────────────┐        ┌───────────────────┐
│ Клиент            │        │ Клиент            │
│ (официальное app) │        │ (переупакованное, │
│                   │        │  Burp, скрипт)    │
└─────────┬─────────┘        └─────────┬─────────┘
          │  идентичные запросы        │
          └────────────┬───────────────┘
                       ▼
             ┌─────────────────────┐
             │  API Gateway / WAF  │   <- авторизация, лимиты, схема
             └──────────┬──────────┘
                        ▼
             ┌─────────────────────┐
             │  Сервисы            │   <- авторизация на КАЖДОМ ресурсе
             └─────────────────────┘
```

Из этой модели следуют три правила:

1. **Клиент не является границей доверия.** Всё, что в приложении
   (ключи, алгоритмы, логика проверок), считается известным атакующему.
2. **Авторизация проверяется на сервере для каждого объекта**, а не «раз уж
   токен валиден».
3. **Контракт важнее реализации**: схема (OpenAPI/GraphQL/protobuf) —
   источник правды для валидации и для тестов.

## Аутентификация и токены

### OAuth 2.0 / OIDC: что проверять в первую очередь

| Элемент                 | Требование                                     | Типовая ошибка                              |
| ----------------------- | ---------------------------------------------- | ------------------------------------------- |
| `redirect_uri`          | точное совпадение со списком                   | префиксная проверка, нормализация пути      |
| `state`                 | одноразовый, привязан к сессии                 | отсутствует -> login CSRF                   |
| PKCE (`code_challenge`) | обязателен для публичных клиентов              | не используется -> перехват кода            |
| `nonce` (OIDC)          | для id_token                                   | отсутствует -> replay id_token              |
| `response_type`         | `code` (OAuth 2.1)                             | `token`/implicit — устарел                  |
| `code`                  | одноразовый, TTL ≤ 60 с                        | повторное использование принимается         |
| `id_token`              | подпись, `iss`/`aud`/`exp`/`azp`               | проверка подписи «если есть»                |
| `refresh_token`         | ротация + обнаружение повторного использования | бессрочный, без ротации                     |
| `scope`                 | минимум, без «всё сразу»                       | `openid profile email offline_access admin` |
| logout                  | отзыв токенов на сервере                       | только очистка клиента                      |

Подробный разбор обходов `redirect_uri` — в
`payloads/web/http/oauth-redirect-uri-bypass.md`.

### JWT: чек-лист валидации

```text
1. alg      -> allowlist (RS256/ES256), никогда не из токена
2. none     -> отклонять всегда
3. RS->HS   -> публичный ключ не должен приниматься как HMAC-секрет
4. kid      -> whitelist идентификаторов, никаких путей/SQL/JNDI
5. jku/jwk/x5u/x5c -> игнорировать, JWKS только из конфигурации
6. iss/aud  -> точное совпадение с ожидаемыми значениями
7. exp/nbf  -> проверять, с допуском на часы (clock skew ≤ 60 с)
8. подпись  -> проверять ДО чтения claims
9. claims   -> роль/права сверять с серверным состоянием, не доверять токену
10. отзыв   -> короткий TTL + revocation list/JTI-кеш для критичных операций
```

Карточки: `jwt-alg-none`, `jwt-weak-secret`, `jwt-kid-injection`,
`jwt-confused-alg-rs2hs`, `cookie-state-forgery`.

### API-ключи и секреты в мобильных клиентах

Встроенный в приложение секрет — **публичный** секрет. Практические правила:

- никаких API-ключей с широкими правами в клиенте;
- доступ к данным — через свой backend (паттерн BFF, backend-for-frontend),
  клиент получает короткоживущий токен с узкой областью;
- если ключ неизбежен — он должен быть ограничен по referrer/IP/scope
  и поддаваться ротации;
- обфускация и «шифрование в нативном коде» не являются защитой,
  только поднимают стоимость анализа.

## REST и BOLA: авторизация на уровне объекта

`BOLA` (Broken Object Level Authorization, он же IDOR) — самая частая находка
в API по версии OWASP API Security Top 10. Проверка занимает минуту, но требует
двух учётных записей.

```bash
# сессия пользователя A, объект пользователя B
curl -s -H "Authorization: Bearer $TOKEN_A" https://api.example/v1/orders/1042
curl -s -H "Authorization: Bearer $TOKEN_A" https://api.example/v1/orders/1042/items
curl -s -X PATCH -H "Authorization: Bearer $TOKEN_A" \
     -H 'Content-Type: application/json' -d '{"status":"refunded"}' \
     https://api.example/v1/orders/1042
```

Проверять нужно не только основной ресурс, но и:

- вложенные коллекции (`/orders/{id}/items`, `/users/{id}/documents`);
- побочные эндпоинты (`/export`, `/pdf`, `/preview`, `/history`);
- фильтры и поиск (`?user_id=2`, `?owner=`);
- GraphQL-резолверы, доступные через другую связь схемы;
- массовые операции (`POST /orders/bulk`);
- **mass assignment**: добавление в тело `{"role":"admin"}`, `{"owner_id":2}`,
  `{"is_verified":true}`.

Правильная реализация — проверка владения в слое сервиса, а не «спрятать
ссылку в UI»:

```python
order = repo.get(order_id)
if order.owner_id != current_user.id and not current_user.is_support:
    raise Forbidden()          # одинаковый ответ для «нет» и «не существует»
```

## GraphQL

Отдельный набор проблем (карточка `logic-graphql-introspection-batching`):

1. **Introspection** в production — полная карта схемы за один запрос.
2. **Авторизация на резолверах**, а не на корневом запросе: `Query.viewer`
   защищён, а `User.email`, доступный через другую связь, — нет.
3. **Батчинг** — массив операций в одном HTTP-запросе обходит rate limiting.
4. **Глубина и сложность** — вложенность и алиасы дают DoS
   (`{a1: user {friends {friends {…}}}}`).
5. **Мутации без идемпотентности** — повтор создаёт дубли заказов.
6. **Утечка ошибок** — стектрейсы резолверов с SQL и внутренними путями.
7. **Запросы в GET** — кэшируются прокси и попадают в логи с аргументами.

Меры: `introspection: false`, query depth/complexity limits, лимит алиасов,
persisted queries (allowlist операций), авторизация в каждом резолвере,
общий текст ошибок клиенту.

## gRPC и protobuf

- gRPC по умолчанию **не шифрует** (`insecure` channel) — в production только TLS;
- рефлексия (`grpc.reflection.v1alpha.ServerReflection`) в production —
  аналог GraphQL introspection: отключить;
- авторизация по метаданнывым interceptor'ам, а не «внутри одного метода»;
- protobuf-поля с `optional`-семантикой: отсутствие поля ≠ пустое значение —
  логические ошибки при частичном обновлении;
- лимиты размера сообщения (`max_receive_message_length`) против DoS.

## Мобильные приложения

### Хранилища и секреты

| Хранилище                        | Что проверяем                                                                   |
| -------------------------------- | ------------------------------------------------------------------------------- |
| iOS Keychain / Android Keystore  | корректность `kSecAttrAccessible`, наличие аппаратной привязки                  |
| SharedPreferences / UserDefaults | секреты в открытом виде, бэкап (`allowBackup="true"`)                           |
| Локальные БД (SQLite/Realm)      | шифрование (SQLCipher), права на файл, экспорт через бэкап                      |
| Кэш HTTP                         | `Cache-Control`, кэширование токенов и персональных ответов                     |
| Логи                             | токены/PII в logcat/os_log, уровень логирования в release                       |
| Буфер обмена                     | копирование паролей и одноразовых кодов                                         |
| Клавиатура                       | сторонние клавиатуры для полей ввода (`disableAutocorrection`, `noSuggestions`) |

### Транспорт и конфигурация

- **iOS ATS** / **Android Network Security Config**: разрешены ли cleartext и
  произвольные CA; custom trust anchors в release-сборке — красный флаг;
- **SSL pinning**: есть ли, как реализован (сертификат vs SPKI vs публичный ключ),
  покрывает ли все эндпоинты, есть ли fallback;
- **Deep links / App Links / Universal Links**: перехват scheme-ссылок другим
  приложением, передача токенов в URL, отсутствие проверки источника;
- **WebView**: `setJavaScriptEnabled` + `addJavascriptInterface` (API < 17 — RCE),
  `setAllowFileAccess`, загрузка произвольных URL;
- **Экспорт компонентов**: `exported="true"` у activity/service/receiver
  без permission, content providers с `grantUriPermissions`;
- **Биометрия**: проверяется факт успешной аутентификации, а не «наличие
  отпечатка на устройстве» (`BiometricPrompt` + `CryptoObject`).

### Reverse engineering и защита клиента

Реалистичная позиция: **обфускация и anti-tamper не являются контролем
безопасности**, они лишь повышают стоимость атаки. Все критичные проверки
должны дублироваться на сервере. Что действительно стоит делать:

- минимизация логики на клиенте (серверная валидация сумм, прав, лимитов);
- обнаружение root/jailbreak и отладчика — как сигнал риска для step-up
  аутентификации, а не как блокировка (иначе ломаются легитимные пользователи);
- целостность сборки: подпись артефактов, Play Integrity / App Attest
  для критичных операций;
- защита от переупаковки — через серверную проверку аттестации, а не
  через само приложение.

## Практика

Лаборатории для API-части:

```bash
# локальный API-стенд: два пользователя, заказы, GraphQL-эндпоинт
cd labs/setup
docker compose --profile api up -d      # (появится в Фазе 2, см. ROADMAP)
```

Задания (до появления стенда — на своём pet-проекте):

1. Соберите список всех эндпоинтов из OpenAPI/из трафика приложения
   (Burp -> «Content discovery» по записанным запросам).
2. Заведите две учётки и пройдите матрицу BOLA: каждый эндпоинт × чужой объект
   × методы GET/PUT/PATCH/DELETE. Зафиксируйте результаты таблицей.
3. Проверьте mass assignment: добавьте в тело `role`, `owner_id`, `is_verified`,
   `balance`, `created_by`.
4. Для GraphQL: включён ли introspection, есть ли лимит глубины, работает ли
   батчинг, авторизованы ли резолверы.
5. Проверьте JWT по чек-листу из 10 пунктов; отдельно — поведение при
   отсутствующем/неверном `kid`.
6. OAuth-flow: подмена `redirect_uri` пятью способами, отсутствие `state`,
   повторное использование `code`, отсутствие PKCE.
7. Мобильное приложение (своё или учебное): распакуйте APK/IPA, найдите
   хранилища, проверьте `allowBackup`, сетевой конфиг, наличие hardcoded-ключей.
8. Для каждой находки сформулируйте серверное исправление и тест в CI.

## Чек-лист ревью API

- [ ] OpenAPI/GraphQL-схема соответствует реализации; расхождений нет.
- [ ] Авторизация проверяется для каждого объекта (BOLA), включая вложенные
      ресурсы и экспорт.
- [ ] Mass assignment исключён: DTO/whitelist полей, никаких `role`/`owner_id`
      из клиента.
- [ ] JWT: allowlist алгоритмов, проверка подписи до claims, валидация
      `iss/aud/exp/nbf`, whitelist `kid`, игнорирование `jku`/`x5c`.
- [ ] OAuth: точный `redirect_uri`, `state`, PKCE, одноразовый `code`,
      ротация refresh-токенов.
- [ ] Rate limiting по операциям (не по HTTP-запросам), отдельный лимит на
      аутентификацию и на «дорогие» эндпоинты.
- [ ] Идемпотентность для POST-операций, влияющих на деньги/состояние.
- [ ] GraphQL: introspection выключен, depth/complexity/aliases лимиты,
      persisted queries, авторизация на резолверах.
- [ ] gRPC: TLS, рефлексия отключена, лимиты размера сообщений.
- [ ] Ошибки не раскрывают стектрейсы, SQL, внутренние имена сервисов.
- [ ] Логи не содержат токенов, паролей, PII; уровни логирования для release.
- [ ] Версионирование и депрекация: старые версии не остаются без проверок.
- [ ] Клиент не содержит секретов с широкими правами; критичные операции —
      через backend.
- [ ] Корпоративные требования: аудит-лог обращений к чувствительным данным,
      алерты на массовое чтение.

## Связи в графе

Узлы `jwt`, `auth-bypass`, `business-logic`, `race-condition` и `graphql`
связаны рёбрами `leads_to` к `session-hijacking` и `data-exfiltration`:
в API-модели утечка данных почти всегда начинается с авторизации на уровне
объекта, а не с «классической» инъекции.
